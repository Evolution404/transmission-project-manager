# 项目/需求/物资模型重构交接（2026-09-12）

## 1. 本轮用户最终业务纠偏

当前 P2/P3 的核心模型假设需要重构。以下是用户最新明确的业务事实，优先级高于旧文档中“需求物资先完整确定再转储备”的表述：

1. 项目储备阶段并不清楚全部物资需求，**不能要求用户先一次性上传/录完所有物资才能建立储备项目**。
2. 项目后续的实际物资需求会发生变化：可以新增、减少、替换型号、调整数量；系统必须保留修订历史，不能静默覆盖历史事实。
3. **“需求”不是“最终项目物资清单”的同义词。** 需求是具体业务/隐患台账，可以包含线路、杆段、类别、电压、技术字段，以及当时已经明确的物资型号和数量；但这些物资信息可以为空、可以不完整，也不能成为后续项目物资需求的硬上限。
4. 凡系统提供批量导入的业务对象，必须同时提供手工新建入口；导入只用于批量提效，不能成为唯一创建方式。
5. 物资还存在供应/履约状态，例如：**已上报、已发货、已到货**等。状态不能挂到全局标准物资字典上，而必须属于“某项目的某项物资需求/供货批次”。
6. 同一物资需求可能部分数量处于不同状态，例如项目需要 100 套时，可以同时存在：100 已上报、60 已发货、20 已到货。因此禁止用一个单值枚举覆盖整条项目物资需求的真实进度。

### 1.1 WorkBuddy 参考项目已通过本机 Chrome CDP 实际核验

参考页面：`https://www.workbuddy.link/p/plhvulKoyaQX5vic8Oaeoy?source=2`。2026-09-12 已通过本机独立 Chrome 调试实例读取真实 DOM 和页面脚本，不再只依赖旧截图/文字印象。

已确认的参考逻辑：

- 页面主线明确写为 `项目需求 → 项目储备（物资明细汇总，关键环节） → 出库项目 → 项目实施 → 项目结算`；
- “项目需求（隐患台账）”每条可直接包含线路、杆段、类别、电压、物资型号、数量、跨越对象等，说明需求阶段可以有具体物资信息；
- 从需求勾选生成储备时，页面脚本同时保存 `reqIds`（关联需求）和复制出的 `items`（储备物资明细），说明“需求来源关系”和“储备项目物资”实际上是两个概念；
- 手工“新建储备项目”代码只强制项目名称，允许 `reqIds=[]`，物资 textarea 为空时 `items=[]` 仍可保存，因此**储备项目不依赖完整需求或完整物资先存在**；
- 储备详情单独展示“关联需求 N 条”和“物资明细”，进一步证明二者不应在正式系统中被一张 `demand_allocations` 表混成同一事实；
- 参考演示版把同一个储备对象用单值 `stage` 从 `reserve → out → impl → settled` 推进，并在确认实施/结算时批量把全部关联需求标记完成。这只是演示简化，正式系统不要照抄；当前 P5 的分批出库、部分实施、独立结算和历史保护更严谨，应保留；
- 参考项目**没有**“已上报 / 已发货 / 已到货”供应状态。这部分是用户在本轮新增的正式业务要求，属于参考项目基础上的扩展。

因此本轮重构不是照搬 WorkBuddy，而是保留它正确的业务分层，同时修掉它的浏览器本地存储、单值阶段、全量完成等演示级简化。

## 2. 新的业务主线

目标主线应改为：

```text
业务需求
  ↓（可关联一个或多个）
项目储备
  ↓
项目物资需求（可以为空，持续修订）
  ↓
物资供应/履约（已上报 → 已发货 → 已到货……，按数量/批次追踪）
  ↓
项目出库范围
  ↓
实施
  ↓
实际物资使用
  ↓
结算
```

注意：供应状态和项目“出库/实施”是两条不同事实链。不要把“已到货”自动解释为“已出库”，也不要把“已发货”自动解释为“已实施”。

## 3. 对象职责必须彻底拆开

### 3.1 `demands`：业务需求 / 隐患台账

回答：**具体要解决什么隐患/工作需求？当前已经知道哪些业务信息？**

建议核心字段：需求编号/序号、年度、电压等级、线路、杆段、类别、需求描述/技术字段、提出人/负责人、来源、版本、创建时间。需求可以同时携带当时已知的物资型号、数量、价格等初步信息，但这些字段不是建立需求或项目储备的强制前提。

创建来源：

- `manual`：手工创建；记录创建人、创建时间；不得伪造 Excel 文件名/工作表/行号。
- `import`：标准模板或兼容表格导入；保留文件 SHA-256、文件名、工作表、物理源行号、原始字段。

需求创建时**物资可以为 0 条**。

### 3.2 需求阶段物资：当时已知的初步物资信息

需求阶段可以有真实、具体的物资型号和数量，参考项目的需求台账就直接展示“物资型号 × 数量”。但这只表示**需求提出/导入时已经掌握的物资信息**：可以为空、可以只是一部分、也可能在后续复勘和实施准备中变化。它不是项目后续物资的硬上限，也不能继续作为项目生命周期的唯一物资真相。

建议改名/语义为类似：

- `demand_material_estimates`
- 或保留 `demand_materials` 表名但重新定义为“需求阶段估算物资”，并在代码/文档中明确其非权威性。

需求阶段预计 A=100，不意味着项目最终必须是 A=100。项目后续可能变为 A=80 + B=20。

### 3.3 `project_demand_links`：需求和项目的多对多关联

回答：**这个项目是因哪些业务需求产生的？**

需求和项目之间不要再通过“物资分配数量”承担立项关系。建议增加独立链接表：

```text
project_demand_links
- project_id
- demand_id
- relation/note（必要时）
- created_by/created_at
```

一个需求可进入多个项目，一个项目也可承接多个需求。

### 3.4 `projects`：项目储备/业务执行单元

回答：**准备立什么项目？**

项目允许在：

- 没有任何物资需求时创建；
- 物资只明确了一部分时创建；
- 后续持续补充和调整物资。

项目创建最低条件不应再依赖“至少选择一条需求物资”。

### 3.5 `project_material_requirements`：项目当前物资需求

回答：**这个项目当前预计真正需要什么、多少？**

这是后续出库、供应、实施物资数量保护的主对象。建议至少包含：

```text
project_material_requirements
- id
- project_id
- material_id nullable
- raw_model / model
- unit
- required_quantity_scaled
- active/current version info
- created_by / created_at / updated_at
```

来源可以是：

- 手工新增；
- 从需求阶段物资估算复制；
- 批量导入（如果未来提供，则必须同时保留手工新增）。

不要把它继续强绑定为 `demand_material_id + allocation <= 原需求数量`。

### 3.6 项目物资修订历史

项目物资需求必须可追溯修订，不能直接覆盖旧值后失去历史。

可选方案：

- 版本快照：`project_material_requirement_versions` / 项目物资版本快照；
- 或事件式修订：追加 change event，当前态由有效事件投影。

无论选哪种，必须能回答：

- 最初报了多少？
- 哪天改为多少？
- 为什么改？
- 谁改的？
- 哪个出库/实施事实基于哪个版本？

## 4. 物资供应/履约状态设计

### 4.1 状态属于项目物资，不属于标准物资字典

全局 `materials` 只负责标准编码/名称/型号/单位等字典信息。

“已上报 / 已发货 / 已到货”属于具体项目中的物资供应过程。相同标准物资在项目 A 可以“已到货”，在项目 B 可以仍“已上报”。

### 4.2 禁止只存一个 `status`

不要设计成：

```text
project_material_requirements.status = 'arrived'
```

因为会丢失部分履约事实。一个项目需要 100 套时，可以同时：

```text
当前需求：100
已上报：100
已发货：60
已到货：20
```

建议采用**按数量的供应事件/批次模型**。可选择：

#### 方案 A：供应批次/批号

```text
material_supply_batches
- id
- project_material_requirement_id
- quantity_scaled
- current_stage
- reported_at
- shipped_at
- arrived_at
- note
- version
```

部分推进时可以拆批次，例如 100 已上报后其中 60 发货，则拆成 60 `shipped` + 40 `reported`。历史变更必须审计。

#### 方案 B：追加式供应事件

```text
material_supply_events
- id
- project_material_requirement_id
- event_type: report / ship / arrive / adjust / cancel ...
- quantity_scaled
- business_date
- note
- created_by
- created_at
```

当前阶段数量由服务端投影。若采用事件模型，要特别测试重复事件、冲销/更正、并发和数量守恒。

下一位 AI 可选择实现复杂度更合适的一种，但必须满足下述不变量。

### 4.3 最低状态集合

用户已经明确至少需要：

- 已上报
- 已发货
- 已到货

是否还需要“待上报、已审核、已领用、退货、取消、缺货”等，不要擅自扩大正式业务口径。可以预留扩展能力，但先把用户已确认的三个阶段正确实现。

UI 可派生显示“待上报/未上报”等剩余量，但不要把未经确认的业务状态写死为正式流程。

### 4.4 数量不变量

至少锁定：

```text
到货数量 <= 发货数量 <= 上报数量
```

对当前需求数量：

- 尚未发生供应事实时，需求可以自由增减/移除；
- 已发生上报/发货/到货后，不允许通过直接修改项目需求把这些历史事实抹掉；
- 如果业务确实需要把项目需求降到已上报数量以下，应通过显式取消/调整/冲销记录处理，而不是覆盖原值。

因此不要简单规定永久的 `reported <= required` 后又让用户无法处理需求减少；应设计显式修订/取消路径并保留历史。

## 5. 出库 / 实施 / 实际用量仍是独立事实

当前 P5 的关键原则仍保留：

- 项目出库不是仓库物资物流状态；
- 正常实施关联已出库范围；
- 实施完成量与实际物资使用量分开；
- 结算与实施独立；
- 已出库、已实施、有效结算不能被后续项目物资修订静默删除。

重构后保护下限应从旧 `demand_allocations` 迁移到新的 `project_material_requirements`。

典型展示应能同时看到：

```text
当前项目需求 100
已上报 100
已发货 60
已到货 20
已进入项目出库范围 40
已实施 25
实际使用 23
```

这些数字不互相覆盖。

## 6. 导入/手工创建规则

仓库级产品规则：

> 任何提供批量导入的业务对象，必须同时提供逐条手工创建入口。

至少需求必须有：

- `新建需求`
- `批量导入`
- `下载标准模板`

项目物资需求如果未来增加批量导入，也必须同时保留 `新增物资需求` 手工入口。

建议保留 repository guard 测试或页面行为测试锁住这条规则，避免后续又出现“只能导入不能新建”。

## 7. 需要重构/替换的旧假设

旧模型以下假设不再成立：

1. `demands.source_batch_id` 永远必填，需求必须由 Excel 产生；
2. 创建项目必须至少有一条 `demand_allocations`；
3. 项目物资只能来自 `demand_materials`；
4. 项目物资总量永远不能超过原始需求物资数量；
5. “需求→物资数量分配→项目”是唯一立项路径；
6. `demand_allocations` 同时承担“项目和需求关联”与“项目物资需求”两种职责。

建议把“业务来源关联”和“项目物资计划”拆成不同对象，不要继续给 `demand_allocations` 打补丁。

认证仍锁定：

- 系统自维护 username + password；
- 浏览器 Web Worker Argon2id；

- 历史事实不可静默覆盖；
- 幂等、版本、并发、审计必须服务端保证；
- 本地/合成测试不能冒充生产 P7 验收。

## 11. 重构完成的业务验收例子

至少能完整演示：

```text
1. 手工新建需求：220kV XX线 #10-#20 防鸟治理，暂时没有物资。
2. 直接建立储备项目 P001，并关联该需求；项目物资仍为空。
3. 后续现场确认项目需要 A 100 套，手工新增项目物资需求。
4. 供应状态推进：A 上报 100；其中发货 60；其中到货 20。
5. 项目需求调整为 A 80 + B 20，并保留原 100 的修订历史；如果已有供应事实导致不能直接降量，要给出明确的调整/取消路径而不是抹历史。
6. 到货和供应状态不自动生成项目出库。
7. 项目单独出库 A 40，实施 25，实际使用 23。
8. 页面同时显示：当前需求、已上报、已发货、已到货、已出库、已实施、实际使用、结算覆盖，各自可追溯。
```

只有这条链路和自动测试都成立，才算本次模型重构真正完成。
