# 代码与操作界面审查（2026-09-15）

## 1. 本轮目标

在不改变已定稿业务模型的前提下，继续收敛基础台账实现中的正确性、性能和操作复杂度。

本轮不修改需求/储备/实施/结算/财务业务规则，不推进数据库 migration 版本。

## 2. 已确认问题

### P0：线路状态筛选与服务端分页不一致

当前 `/master/lines` 服务端分页后，Web 再对已加载页执行启用/停用过滤。
这会产生假空结果：当前页没有目标状态时，即使后续页存在匹配线路，界面仍显示“没有符合条件的线路”。

改法：把 `enabled` 作为服务端查询条件，筛选发生在分页之前。

### P1：旧杆塔批量接口仍暴露技术排序字段

正式产品已使用 `/towers/import-chunk` + `/towers/reorder`，但旧 `/towers/batch` 仍允许调用并接受 `sortRank`。
它保留了已废弃的“1–20 行 + 用户技术排序值”合同，增加维护和绕过新业务模型的风险。

开发阶段无兼容要求，本轮删除该接口、Port、Repository 实现和旧测试。

### P1：基础台账单文件职责过多

`MasterDataView.vue` 同时承担：查询、分页、错误状态、属性编辑、更名、历史、排序、文件导入、断点续传及全部 UI。
当前约 600 行，继续加功能会提高耦合和回归成本。

本轮先抽统一 API client，并收敛页面动作；后续再按稳定边界拆 composable / 子组件，不为拆文件而拆文件。

### P1：移动端顺序调整不可靠

当前短距离排序依赖原生 HTML drag/drop。触屏设备没有可靠的等价操作。

改法：保留桌面拖动，同时每行提供“上移/下移”；长距离继续使用“移动到目标前/后”。

### P1：允许同号后，排序目标无法区分

顺序编辑两个下拉框只显示 `tower_no`。当两个稳定 `tower_id` 当前编号相同时，用户无法判断选中了哪一个。

改法：选项显示当前物理序号 + 杆塔编号 + 类型，稳定 ID 仍作为 value。

### P1：操作按钮过密

线路详情头部一次出现 6 个按钮，杆塔每行出现 4 个按钮。桌面信息密度高，手机端更明显。

改法：高频动作直接展示；低频/危险动作进入“更多操作”菜单。删除保持明确的危险动作语义。

### P2：线路列表查询存在逐行 COUNT 子查询

`listLines()` 对每条线路执行相关 `COUNT(*)` 子查询统计杆塔数量。

改法：改为一次按线路分组的聚合子查询 JOIN；列表页仍保持单次数据库 query。

### P2：页面重复 API client

多个 View 各自实现相同的 `apiRequest()`，幂等 JSON 请求辅助也分散。

改法：新增统一 Web API client，先迁基础台账；后续逐页迁移，避免一次跨全站大改。

### P2：局部动作后过度刷新

例如删除杆塔后会重新读取电压等级、线路和杆塔；部分保存路径也会重复取不相关数据。

改法：按对象类型做最小刷新，避免不必要网络请求。

## 3. 第一阶段实施顺序

1. 服务端线路 `enabled` 筛选及分页回归测试。
2. `listLines()` 杆塔数改为聚合 JOIN。
3. 删除旧 `/towers/batch` 及死代码 `findLastTowerRank()`。
4. 新增统一 Web API client，基础台账迁入。
5. 线路/杆塔操作区重构为“高频动作 + 更多菜单”。
6. 顺序编辑器增加可触屏的上移/下移，并让同号选项可区分。
7. 修复 stale error、杆塔加载状态和不必要的全量刷新。
8. 定向测试 + 完整 `npm run check`，小提交并及时 push。
