## 3. 真实业务数据验收原则

真实资料进入系统不得为了“导得进去”而破坏当前业务不变量：

- 电压等级、线路、杆塔必须先进入基础台账；正式需求只引用台账对象。
- Excel 文字输入必须解析到已有且启用对象；未知/停用对象阻断发布，禁止自动建线路或杆塔。
- 需求是抽象事项，需求物资只是 0..N 条已知信息，不构成项目物资上限。
- 项目需求来源关系和项目物资是独立事实；项目物资调整必须有修订历史。
- 项目只做一次项目级出库；出库后建立多个任务，而不是恢复逐物资 release line 主模型。
- 任务供应满足 `到货 <= 发货 <= 上报 <= 任务需求`；实施和结算独立，允许先结算后实施。
- 部分进度不能伪装成完成；四状态由任务事实回投。
- 缺价格不等于零价格；金额使用整数分/定点运算，不做浮点累计。
- 预算、预算发生、实际费用、结算、协议额度保持独立。
- 历史月报不可被当前规则覆盖；月份精度事项不得捏造具体日期。
- 已发生供应、实施、结算和历史台账引用不能被后续编辑静默删除。

真实业务文件只在受控本地/私有存储中处理，不提交 GitHub，不写入测试 fixture。

## 4. 正式资源与配置核对

正式验收前必须读取实际状态，而不是沿用本地 `wrangler.jsonc` 占位配置。至少核对：

- Worker/Static Assets 与自定义域名；
- D1 database ID、当前 migration、备份策略；
- 当前对象存储 provider、非敏感资源 ID、附件和备份 key；
- Cron triggers；
- `APP_ENV=production`；
- Secret 是否存在且位置正确；
- `workers_dev` / preview URL 暴露策略；
- GitHub Environment 和发布服务身份。

Secret 值、Global API Key、长期个人 Token 不得写入验收文档。

## 5. 性能与规模

目标业务规模仍按约 5 万需求行、通常不超过 5 人并发验收。正式环境重点记录：

- 常用列表 P95；
- 登录/Argon2id 在低性能手机上的实际体验；
- Worker CPU time 与异常率；
- D1 read/write rows 与查询次数；
- 对象存储用量/错误率；Notion 模式含 429/5xx，R2 模式含存储/A-B 类操作；
- 导入分片重试和中断恢复；
- 基础台账父级分页、需求列表、分析页面是否存在全量加载或 N+1。

性能目标是验收标准，不是未测试前的承诺。

## 6. 备份恢复边界

当前 D1→`ObjectStorePort` 备份是按表、按 rowid 分片的逻辑导出，不是数据库级跨表一致快照。正式恢复验收必须：

1. 建立可靠停写窗口；
2. 完成业务 D1 备份和当前对象存储附件清单/本体核对；
3. 恢复到隔离 D1；
4. 对账基础台账、需求位置、项目/任务、数量、金额、状态、规则和版本；
5. 确认 `auth_sessions` 未恢复；
6. 演练回退后再结束停写。

## 7. 发布门禁

当前仍处开发阶段，数据库不维护历史升级链；代码要求唯一基线 `0001_initial_schema.sql`。生产 schema 与当前基线不一致时，正式发布流程应优先把历史数据迁移到当前 `0001` 新模型，而不是追加 `0002+` 或让应用继续兼容旧模型；存在无法确定性转换的数据时必须在生产变更前停止并由用户决定。只有用户明确宣布进入运行阶段/正式维护升级链后才允许冻结基线。

任何正式 migration、Secret 变更、域名切换、代码部署、回退和 `main` 合并均需当次用户授权。发布成功不能只看 HTTP 200，至少需要：

- `/api/health` 的 `schema.ready=true`；
- 管理员登录与会话；
- 基础台账读取和需求级联；
- 一个只读接口与一个安全的业务写入冒烟；
- 备份/恢复路径仍可用；
- 版本/提交 SHA 有记录。
