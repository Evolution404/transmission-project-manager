# 基础台账线路中心化重构计划

版本：2026-09-14。

本计划用于实施“电压等级 → 线路 → 杆塔”基础台账第二轮重构。长期业务事实同步维护在 `BUSINESS_BASELINE.md`、`DESIGN.md`、`DATA_MODEL.md`；本文件只定义本次施工范围、顺序和验收标准。

## 1. 重构目标

当前三级数据关系继续保留，但不再把数据库层级原样映射为三列界面。最终交互以“线路”为主对象：

```text
基础台账首页
  └─ 线路列表（电压等级仅作为轻量筛选/标签）
       └─ 线路详情
            └─ 全宽杆塔清单
```

同时完成以下业务能力：

1. 杆塔编号统一规范化，数据库只保存标准形式。
2. 杆塔编号与线路实际顺序彻底解耦。
3. 用户可手工调整杆塔顺序，支持拖拽和“移动到某杆塔前/后”。
4. 线路名称、杆塔编号支持正式更名；稳定对象 ID 不变。
5. 旧名、新名都可追踪、搜索；名称/编号允许重名和后续复用，不能作为对象唯一身份。
6. 杆塔批量导入取消用户可见的“最多 20 条”限制；浏览器全量解析/预检，后端内部小批幂等提交并支持断点继续。
7. 保持当前开发阶段单一 `0001_initial_schema.sql` 基线，不新增 `0002+` migration，也不为旧 schema 建兼容路径。

## 2. 数据身份原则

### 2.1 稳定身份

- 线路唯一身份：`line_id`。
- 杆塔唯一身份：`tower_id`。
- `line_name`、`tower_no` 都只是某一时段使用的业务标识，不是对象身份。
- 同一电压等级允许同名线路；同一线路也允许不同对象在不同时段甚至同一时期使用相同规范杆塔编号。
- 搜索名称/编号必须返回 `0..N` 个候选；命中多对象时禁止自动猜测。

### 2.2 更名历史

线路新增历史表：

```text
transmission_line_name_history
- id
- line_id
- line_name
- valid_from
- valid_to
- changed_by
- change_reason
- created_at
```

杆塔新增历史表：

```text
transmission_tower_no_history
- id
- tower_id
- line_id
- tower_no
- valid_from
- valid_to
- changed_by
- change_reason
- created_at
```

当前名称/编号继续保存在 `transmission_lines.line_name`、`transmission_towers.tower_no`，便于常用读取；历史表保存已结束的名称/编号时段。正式“更名”必须在同一原子写入中完成：版本校验 → 记录旧名历史 → 更新当前名称/编号 → 审计 → 幂等记录。

普通“编辑属性”不得修改 `line_name` 或 `tower_no`，避免绕过历史链。名称变化只能走专用更名接口。

## 3. 杆塔编号规范化

### 3.1 标准格式

数据库中的 `tower_no` 只允许：

```text
#主号
#主号-支号
```

规则：

- 主号和支号都必须是正整数。
- 主号 `1..999` 固定补成三位：`1 → #001`、`10 → #010`、`100 → #100`。
- 主号 `>=1000` 正常表示：`3058 → #3058`。
- 支号不补三位：`10-1 → #010-1`、`10-01 → #010-1`。
- 去除无意义前导零。
- 可接受明显输入法等价字符，例如全角 `＃１０－１`，先转半角再规范化。
- 不进行语义猜测；`G1`、`10A`、`10+1`、`10-1-2`、`10/1`、`0`、`10-0` 等直接拒绝。

唯一规范化函数放在共享业务包，由前端预览与服务端强制校验共同调用。前端校验只改善体验，后端校验才是最终门禁。

### 3.2 名称可重复

删除以下旧唯一约束：

- `UNIQUE(voltage_level_id, line_name COLLATE NOCASE)`
- `UNIQUE(line_id, tower_no COLLATE NOCASE)`

保留稳定主键和线路排序位置唯一性。

## 4. 杆塔顺序模型

### 4.1 编号与顺序解耦

杆塔至少包含：

```text
tower_id   稳定身份
tower_no   当前规范编号，可更名
sort_rank  当前线路位置，可调整
```

修改编号不自动改变顺序；调整顺序不改变编号。

### 4.2 稀疏排序值

现有 `sort_index` 重构为内部 `sort_rank`。用户不直接输入技术排序值。

初始化可按固定间距生成，例如：

```text
1000, 2000, 3000, 4000 ...
```

插入两项之间优先取中间值；局部间隙耗尽时仅对必要范围重平衡。数据库继续保证同一线路 `sort_rank` 唯一。

线路增加独立 `tower_order_version`，新增/删除杆塔、批量重排、拖拽和“移动到”都会递增；线路名称/编码等普通属性继续使用线路自身 `version`，两类并发互不干扰。

### 4.3 用户操作

普通新增杆塔：

- 必填：杆塔编号。
- 可选：杆塔类型。
- 位置默认：线路末尾。
- 可选择“放在某杆塔前/后”。

调整顺序模式提供：

- 短距离：拖拽。
- 长距离：搜索目标杆塔，选择“放在目标前/后”。
- 成功后提供明确结果提示和可选撤销入口；服务端仍以版本和幂等保证一致性。

## 5. 页面重构

### 5.1 基础台账首页

取消桌面三列“电压等级 / 线路 / 杆塔”。

顶部：

```text
电压等级筛选 | 线路搜索 | 状态筛选 | 新增线路 | 导入台账 | 台账设置
```

主体为全宽线路列表。电压等级只作为线路名前轻量标签，不单独占一列或主面板。

“台账设置”用于维护电压等级字典；新增/编辑线路时仍从统一电压等级对象中选择。

### 5.2 线路详情

进入线路后全宽显示杆塔清单：

```text
线路名称 + 电压等级 + 杆塔数 + 状态
编辑属性 | 线路更名 | 新增杆塔 | 导入杆塔 | 调整顺序
```

杆塔表主要列：显示序号、当前编号、类型、状态、操作。显示序号按当前 `sort_rank` 动态计算，不保存为业务事实。

杆塔操作区分：

- 编辑属性
- 杆塔更名
- 停用/启用
- 删除（仅允许未被业务引用且满足既定约束的对象）

移动端同样采用“线路列表 → 线路详情”，不再模拟三栏层级。

## 6. 批量导入与批量维护

### 6.1 用户侧不暴露 20 条限制

当前前后端“1–20 行”限制从产品层移除。用户一次可提交几十、几百或上千基杆塔。

浏览器负责：

- `.xlsx` / `.csv` / 直接粘贴解析；
- 杆塔编号规范化；
- 文件内重复/格式错误检查；
- 分页拉取必要台账并形成对比预览；
- 将已确认数据自动切分为后端安全小批次。

Worker 不解析大 Excel，也不接收无限大单批数据库写入。

### 6.2 导入预览

导入必须先展示：

- 总行数；
- 新增数；
- 更新数；
- 无变化数；
- 冲突/错误数；
- 每条错误对应的源行和原因。

存在阻断错误时禁止开始写入。

### 6.3 两种模式

默认“新增 / 更新”：

- 新杆塔追加到线路末尾；
- 已有对象只更新明确允许的属性；
- 不改变已有杆塔顺序。

“按完整文件顺序重排”：

- 必须明确勾选；
- 文件行顺序成为整条线路顺序；
- 只有文件能完整、无歧义地对应当前线路对象集合时才允许整体重排；
- 不完整清单不得悄悄重排未出现对象。

### 6.4 内部分片

前端自动分批提交；具体批次大小属于内部性能参数，初始值由现有 D1/Workers Free 边界和测试决定，不在 UI 中展示。

每批使用独立幂等键和明确进度；失败后停止并允许从失败批次继续，成功批次不重复写入。

## 7. 搜索与历史追踪

线路搜索同时覆盖：

- 当前线路名；
- 历史线路名。

杆塔搜索先规范化用户输入，再覆盖：

- 当前杆塔编号；
- 历史杆塔编号。

名称/编号允许重名，搜索结果必须返回所有匹配对象并提供足够上下文区分。业务选择场景如果存在多个候选，必须由用户显式选择稳定对象 ID。

## 8. 历史需求与业务引用

旧的“线路一旦有需求引用，就冻结整条线路所有杆塔编号和顺序”规则取消。

原因：正式需求已经保存稳定的 `line_id/start_tower_id/end_tower_id`，历史对象身份不依赖当前名称和当前排序值。

新规则：

- 线路被引用后仍不能把对象身份偷偷换成另一个对象；稳定 ID 不变。
- 线路更名、杆塔更名和排序调整允许发生，但必须审计并保留历史。
- 历史需求读取必须按稳定 ID 解析对象，同时保留需求发生时已有的显示快照/来源信息；当前名称变化不能篡改历史来源事实。
- 停用不破坏历史读取；新业务默认不可选择停用对象。

## 9. API / Repository 施工方向

新增/调整至少包括：

- 杆塔编号规范化共享函数和类型。
- 线路列表支持电压筛选、关键字和历史名称匹配。
- 杆塔列表支持编号搜索和历史编号匹配。
- 专用线路更名接口。
- 专用杆塔更名接口。
- 杆塔移动/排序接口，使用 `tower_order_version`。
- 批量杆塔接口取消“产品层 20 条”语义，保留后端受控批量合同或建立分片会话接口。
- Repository 负责在同一事务/batch 中维护当前值、历史、版本、审计和幂等。

正式 API 命名在测试先行阶段锁定，禁止前端绕过专用更名/排序接口直接 PATCH 名称或排序技术字段。

## 10. 测试先行拆分

### M1：编号规范化与 schema

- 正常输入规范化测试。
- 非法格式拒绝测试。
- schema 去除线路名/杆塔号唯一约束。
- `sort_rank`、`tower_order_version`、历史表基线测试。

### M2：更名与历史

- 线路更名保存历史、稳定 ID 不变。
- 杆塔更名先规范化再保存历史。
- 同名/同编号对象允许存在。
- 幂等重放、stale version、失败原子回滚。
- 历史名称/编号搜索可返回多对象。

### M3：杆塔排序

- 新增默认末尾。
- 插入某杆塔前/后。
- 拖拽等价的 move API。
- `tower_order_version` 并发竞争。
- 排序调整不改变 `tower_no` / `tower_id`。
- 必要时局部重平衡且最终顺序唯一。

### M4：批量导入

- 前端大批数据不受 20 条 UI 限制。
- 全量规范化、错误预览、重复/歧义阻断。
- 自动内部切片与断点继续。
- 默认模式不改已有顺序。
- 完整清单模式才允许整体重排。

### M5：线路中心 UI

- 首页不再渲染三列结构。
- 电压等级为筛选/标签，设置入口独立。
- 线路详情全宽杆塔清单。
- 更名、导入、调整顺序入口清晰分离。
- 手机端“线路列表 → 线路详情”。
- 全局中文提示继续通过门禁。

## 12. 最终验收标准

- 数据库只存在 `0001_initial_schema.sql` 单一开发基线。
- 所有杆塔当前编号均为规范格式。
- 名称/编号允许重名，稳定 ID 始终是对象身份真源。
- 线路/杆塔更名历史完整、可搜索、可多结果返回。
- 杆塔顺序可手工调整并与编号解耦。
- UI 不再出现三级三列主界面。
- 用户批量导入不再看到“最多 20 条”。
- 大批杆塔导入由浏览器预检、内部小批幂等写入，可恢复失败批次。
- 定向测试、完整 `npm run check`、GitHub CI 全绿后才允许合并 `main`；部署仍按受保护 production workflow 单独授权执行。
