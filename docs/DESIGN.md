# 设计方案：基于 WorkBuddy 示例的项目全流程管理台

版本：2026-09-13。当前长期业务基线见 `BUSINESS_BASELINE.md`。最终主线为“基础台账 → 抽象需求（可带 0..N 物资子明细）→ 项目储备（需求来源 + 独立项目物资）→ 一次项目级出库 → 多执行任务 → 任务物资供应 / 实施 / 结算三线并行 → 四状态回投需求”。P4 框架/协议/预算发生、P6 分析/提醒/通知/备份和 P1.2 系统自维护认证继续保留；旧 `demand_allocations` / `release_lines` 仅保留历史兼容，不再作为最终主模型。2026-09-13 已完成“电压等级 → 线路 → 杆塔 → 需求定位”对象化重构，下一阶段仍是 P7 真实数据和正式环境验收。

## 1. 目标与已确认条件

为 20 人以内、通常不超过 5 人同时操作的团队提供跨电脑、手机的共享管理台。完整追踪需求、储备、项目出库、实施、结算，管理框架费用、执行协议和子项目预算，并自动生成预警与邮件提醒。

- 不购买传统云服务器；用户后续明确要求不部署中国大陆、不备案，并询问 Cloudflare 免费方案。
- 默认 Cloudflare 免费起步；自定义域名费用另计。不得承诺大陆始终快速或固定经过香港。
- 项目出库指从储备库转入实施，不做采购、入库、库位、盘点等完整仓储系统。
- 需求形成储备由系统建议、人工确认。
- 预算统计口径可配置。业务登录使用系统自维护账号密码；邮箱不是登录条件，也不要求验证。后续邮件通知如启用，作为独立联系方式管理。
- 不在初始化阶段实现业务、创建正式云资源、部署站点或发送邮件。
- 系统必须支持后续完全移交给他人日常管理：不得共享资产所有者的 Cloudflare 密码或个人 API Token；业务管理员在应用内完成日常成员和权限管理，技术维护人员使用自己的 Cloudflare 成员身份或 CI 服务身份维护基础设施。

## 2. 界面与参考

参考页面：[输电项目全流程管理台](https://www.workbuddy.link/p/plhvulKoyaQX5vic8Oaeoy?source=2)。该页面已于 2026-09-12 通过浏览器只读查看，六个模块和储备详情均可见。

界面采用浅色后台、左侧导航、紧凑顶部栏、统一圆角/边框/阴影层级。六个主入口：总览、项目需求、项目储备、实施结算、框架费用、储备分析；另加规则与成员管理。电脑使用分页表格和批量操作，手机优先待办、记录实施与上传附件。没有业务数据时展示真实空状态。Naive UI 全局固定 `zhCN/dateZhCN`，任何未显式填写 placeholder 的输入框/下拉框也只能呈现中文默认文案；禁止回退为 `Please Input/Please Select`。新增需求等低频、大表单操作使用模态框，不占据主页面首屏。

参考观察与改进要求：

- 页面声明数据只保存在当前浏览器：正式版需共享数据库和服务端鉴权。
- UI 正常业务页面不展示 P2/P6 等开发阶段术语；开发阶段、schema 版本等只通过健康接口、日志和运维文档表达。
- 总览已有实施需求，但没有出库项目：不能直接断言数据错误，需支持历史实施与待关联状态。
- 分类映射说明与大类“暂无储备”显示不一致：所有分析必须共用同一映射。
- 已经过的季度仍标“未到”：使用业务年份、时区和季度边界判断。
- 某些储备物资没有价格：显示已知金额/估价完整度，不能将缺价计为零。
- 预算与预算发生记录是两个独立对象：正式设计保留这个区别。

示例中的电力技术文字和映射是参考内容，不是已验证的行业规范。需求导入不依赖预先取得任意历史 Excel：系统提供标准需求模板，用户按模板填报后导入。年度节点和分类资料仍需按真实业务核对；不得编造正式项目、物资单价或法规依据。

## 3. 基础台账与需求定位

设备位置使用严格三级对象关系：`VoltageLevel 1:N TransmissionLine 1:N TransmissionTower`。电压等级由管理员统一维护，线路必须属于电压等级，杆塔必须属于线路。线路/杆塔真实身份由稳定 ID 表达，名称和编号允许更名、重名并保留历史。杆塔编号统一规范为 `#001`、`#010-1`、`#3058` 等形式；用户可输入 `10`、`10-1` 等简写，无法规范化的格式拒绝。真实线路顺序由独立 `sort_rank` 表达，与杆塔编号解耦。

基础台账第二轮重构以线路为主对象推进。当前施工版已完成杆塔编号自动初始插位、专用前/后移动、更名历史，以及 Excel/CSV/粘贴大批导入：用户一次可提交任意规模数据，浏览器先读取完整线路台账进行预检，再自动切成内部安全分片；内部批次大小不作为产品限制暴露。最终 M5 会彻底移除桌面三栏结构，改为“线路列表 → 线路详情”。

正式需求的位置只保存对象引用：`voltage_level_id`、`line_id`、`location_type`、`start_tower_id`、`end_tower_id`。`location_type` 仅允许整线、单塔、连续区段三种形状；手工需求必须按“电压等级 → 线路 → 位置类型 → 杆塔”级联选择，不能自由输入线路或杆塔。

Excel 仍允许用户填写易读的电压、线路和杆段文字，但这些文字只是导入输入。validate/publish 必须解析到已有且启用的台账对象；未知或停用对象阻断发布并提示先维护台账，系统禁止因为导入自动创建线路/杆塔。杆段解析先匹配完整杆塔号，再尝试按区段分隔符拆分，避免把带连字符的合法杆塔号误拆。

历史保护采用保守规则：线路已有需求后不能改变所属电压等级；该线路所有杆塔的换线、改号、顺序调整和删除都冻结，包括区段内部杆塔。对象仍可停用，历史需求继续显示原对象快照；新业务不可选择停用对象。

## 4. 需求池与导入

需求本体的核心字段是序号、电压等级、线路名称、杆段；年度、类别、负责人和类别扩展字段按业务需要补充。物资型号、物资数量、单位属于 0..N 条需求物资子明细，不是需求成立的必填前提。系统标准模板仍可把需求字段与物资字段放在同一行录入，但导入发布时必须规范化为“一个抽象需求 + 多条物资子明细”。同一抽象需求对应的多条 Excel 行全部保留在来源追溯中。

需求物资只是需求阶段已知信息，不是最终项目物资清单，也不形成项目数量上限。原始型号与标准物资型号分开，标准化通过物资字典。没有编码时使用经确认的标准名称、型号、单位组合，不把相似字符串自动认作相同物资。Excel 中的电压文字只作为导入输入；正式发布必须解析到已有 `voltage_level_id`，并由台账对象生成显示快照。

需求支持两种等价入口：**手工新增**和**标准模板批量导入**。凡业务数据存在批量导入能力，必须同时保留逐条手工新建入口，批量导入只能用于提效，不能成为唯一入口。手工新增与模板导入使用同一套服务端字段、数量、电压、标准物资和疑似重复校验。导入过程为：系统下载标准 `.xlsx` 模板 → 用户按模板填报 → 浏览器后台线程解析并自动映射 → 展示错误和疑似重复 → 分批上传暂存 → 服务端校验 → 用户确认发布。已有手工/复用字段映射保留为兼容能力。初始传输分片 20 行，按 CPU 实测调整；单个 SQL 的参数个数仍需单独满足 D1 限制。

需求来源显式区分 `import` 与 `manual`。文件导入保留文件哈希、文件名、工作表和物理行；手工新增只记录真实的手工来源、创建人和原始输入，不伪造 Excel 文件、工作表或行号。

同一文件哈希、工作表、源行重复上传应幂等；业务疑似重复仅提示，不自动删除合法重复需求。不同版本表格有明确源业务 ID 时按 ID 提议变更，没有可靠 ID 时人工核对。导入记录包含新增、跳过、冲突、失败及修正详情。导入批次完成校验后才可见为正式数据，失败不暴露半批正式记录；支持中断续传。

## 5. 项目储备（核心）

操作向导：建立储备项目 → 关联 0..N 个抽象需求作为业务来源 → 独立形成项目自己的当前物资明细 → 持续修订项目物资 → 确认储备版本。**建立储备项目不要求项目物资已经完整，允许 0 条项目物资先立项。**

- 需求来源关系与项目物资必须分开：`project_demand_links` 只说明“项目因哪些需求形成”，不把需求物资数量继承为项目上限。
- 项目物资由 `project_material_requirements` 独立维护，可新增、减少、换型、补充；每次修订必须记录原因和前后快照。项目物资已经分配到执行任务后，不得删除、换型或缩减到任务累计分配量以下。
- 物资数量和单价使用定点整数；`null` 单价表示未知，明确输入的零价仍是有效零价。当前储备类别金额只统计尚未项目级出库的当前项目物资，施工费/其他费不强行摊入项目物资类别。
- 确认储备保存不可变版本；后续项目物资调整回到草稿并产生新的修订历史，再确认形成新的储备版本。项目级出库后保留当时需求来源和项目物资快照，不能通过后续修改重写历史执行事实。

储备项目和框架下的子项目使用同一个业务 ID。储备阶段可暂不关联框架，正式预算发生前必须归属一个框架。一个项目不同时归属多个框架；有该业务需要时拆为独立项目并保留原始需求分配关系。

## 6. 项目级出库、执行任务与三线并行

项目出库是**一次项目级业务状态转换**：已确认储备项目通过 `project_releases` 正式进入执行阶段，并冻结当时的需求来源、项目物资、项目版本和储备版本快照。它不是仓库发货，不填写逐物资出库数量，也不再使用旧 `release_lines` 作为最终模型。同一项目只做一次项目级出库。

只有项目级出库后才能创建正式执行任务。一个项目可以拆成 1..N 个 `project_tasks`；每个任务明确现场范围、计划量、覆盖哪些抽象需求，以及从项目物资中分配哪些任务物资。任务是执行事实的基本颗粒度。

任务内部三条线独立推进：

- **物资供应**：按任务物资数量追踪已上报、已发货、已到货，累计必须满足 `到货 <= 发货 <= 上报 <= 任务物资需求量`；使用独立 `supply_version` 防并发超记。
- **现场实施**：按任务需求范围登记本次完成量，并可登记实际物资使用；使用独立 `implementation_version`。部分完成只显示进度，不等于任务全部实施。
- **任务结算**：按任务需求范围登记覆盖量、金额、最终标记和协议分摊；使用独立 `settlement_version`。结算可以先于实施发生；最终结算必须覆盖任务全部需求范围。首次实施后产生结算提醒，最终结算完成后关闭。

| 实施完成 | 结算完成 | 反馈状态 |
|---|---|---|
| 是 | 是 | 已实施已结算 |
| 是 | 否 | 已实施未结算 |
| 否 | 是 | 未实施已结算 |
| 否 | 否 | 未实施未结算 |

最终四状态从任务事实回投到原始抽象需求：系统汇总该需求在所有任务中的计划范围、实施量和结算覆盖量，再分别判断实施完成与结算完成。项目层状态再由任务汇总。资金线中的预算、预算发生、实际费用、任务结算仍是不同事实，不因执行状态自动互相生成。

## 7. 框架费用、协议、预算和流水

独立账目：框架总额、执行协议预支额度、子项目预算、预算确认占用、预算发生流水、实际发生费用、结算金额。预算确认占用来源于生效预算版本的协议分配，预算发生来源于另外登记的确认流水；不得在登记预算时自动复制一笔预算发生。

一个协议可服务多个子项目，一个子项目可按金额关联多个同框架有效协议。编制预算草稿无需有效协议；确认预算占用或预算发生时必须有关联有效协议。协议暂停/到期不能抹掉历史发生，已发生记录保留当时归属。

| 指标 | 默认口径/阈值 |
|---|---|
| 协议使用率 | 该协议确认预算发生额÷协议额度，达到90%预警 |
| 框架使用率 | 框架确认预算发生额合计÷框架总额，达到80%预警 |
| 预算超框架 | 当前有效子项目预算合计大于框架总额，单独预警 |
| 季度进度 | 当年累计确认预算发生额÷年度目标 |
| 协议预支率 | 有效协议额度合计÷框架总额，独立展示 |

使用率/进度可切换预算确认占用、预算发生、实际发生、结算口径，来源金额分开存储。同一张报表必须显示口径、截止日期、年度目标和配置版本；不同口径金额不能相加。预算总额检查不随进度口径切换消失。

90%、80%、超框架规则默认仅警示并留痕，不擅自增加审批门槛；无有效协议、跨框架归属、重复流水等数据约束则拒绝提交。分母为零时显示未配置，产生配置待办，不返回无穷大或伪造100%。确认流水用调整/冲销留痕，不硬删除。金额按整数分，界面可显示元或万元。历史月报使用当时生效的额度与口径。

## 8. 月度、季度及滞后分析

- 年度目标默认框架金额，跨年度项目单独配置各年目标。
- 默认季末累计目标25%、50%、75%、100%，月度均匀分解，允许自定义月计划；子项目有各自计划，不强制所有子项目同时同比例完成。
- 正式月报针对已结束月份；当月看板标明进行中。季度按年份及季末区分未开始、进行中、已结束，使用 Asia/Shanghai。
- 明显滞后默认实际进度低于同期计划的80%，可改为落后指定百分点。注意“80%计划达成率”与“框架80%使用率”是不同规则。
- 按子项目计划与实际的金额缺口列出重点项目；展示协议未落实、未出库、实施或结算滞后等有记录支持的情况，不自动编造原因。
- 月报保存快照、规则版本及数据截止点；补录或改规则可以生成修订报告，但保留原版。

## 9. 储备大类与年度节点

需求类别、储备大类、项目性质是独立维度。示例初始映射：单改双/备份线夹→防断线；导线接头加固→压接式耐张线夹加固；防钓鱼→防钓鱼。配置版本化，以用户提供的分类文件核对生效。

项目可能覆盖多类，按明细金额归类；共同费用由人工确认分摊。分类金额合计等于项目已知估算金额，每笔只能归属/分摊一次。默认“现状”按仍在库的未出库范围统计；部分出库按分配范围剩余估算金额计算，不把整个项目金额反复计入。可切换全部项目及历史月份快照。未知价格、未分类单列，并显示估价覆盖率。

“一年工作早知道”形成结构化事项表：年度、事项、负责人、关联范围、月份/具体日期、提前提醒和完成状态。仅有月份时在该月开始提醒，并进入未完成摘要；有具体日时默认提前7天、3天、当天提醒。文件中没有日期则标待补充，不让 AI 自行编造。

实施完成生成结算待办，默认30天到期，可按类别配置。已最终结算则关闭待办，撤销结算后重新计算。

## 10. 通知、身份权限、运维移交和备份

### 10.1 登录与业务账号

业务身份完全由系统自身维护，不依赖 Cloudflare Access、邮箱验证码或企业 IdP。用户使用唯一账号 `username` 和密码登录；邮箱不是必填项，不参与认证，也不要求验证。Cloudflare 承载 Workers、D1、域名/WAF；文件与备份统一通过 `ObjectStorePort`，当前 production 使用 Notion，R2 和普通服务器 Filesystem 保持可替换。

应用内角色仍为：管理员、项目管理、实施、财务、只读。管理员负责创建/停用账号、重置密码、分配角色和框架/项目范围；项目管理、实施、财务和只读权限沿用既定业务边界。所有授权在服务端校验，前端隐藏菜单不能替代权限控制。

新用户默认流程：

1. 管理员在“账号与权限”中创建账号，填写账号、姓名、初始密码、角色和授权范围；不要求填写邮箱。
2. 用户打开系统登录页，输入账号和密码。初始密码登录成功后必须先修改密码，在完成改密前不能进入业务页面。
3. 登录成功后服务端生成高熵随机会话令牌；浏览器只保存 HttpOnly 会话 Cookie，数据库只保存令牌哈希和会话状态，不保存明文令牌。
4. 默认会话绝对有效期 7 天；退出、停用账号、管理员重置密码或用户改密都会使相应旧会话失效。关闭浏览器或刷新页面不等于每次重新登录。
5. 忘记密码不走邮箱找回。用户联系管理员，由管理员重置初始密码并强制下次登录修改。
6. 成员离开团队时停用而非硬删除；停用后下一次业务请求立即拒绝，历史操作、审批和审计引用继续保留。

密码不使用明文、可逆加密、普通 SHA-256，也不把慢 KDF 压到 Worker 上。当前基线由浏览器独立 Web Worker 执行 Argon2id，参数为 `m=19456 KiB`、`t=2`、`p=1`、输出 32 bytes、版本 19，每账号随机 16-byte salt；服务端只计算 `HMAC-SHA256(AUTH_CREDENTIAL_PEPPER, derivedCredential)` 并保存 verifier。浏览器派生凭据属于密码等价凭据，只能通过 HTTPS 发送，不得写入 localStorage、日志或数据库。无 MFA 时最小密码长度 15、最大 128，允许 Unicode、空格和密码管理器生成的长口令，不设置无意义的字符组合规则。

登录失败采用统一错误信息，避免区分“账号不存在”和“密码错误”；连续失败达到阈值后短时锁定，并写安全审计。首个真实管理员仍不得采用“谁先访问谁就是管理员”：一次性 bootstrap 必须在账号表为空时由部署 secret 授权，成功创建后关闭。最后一个启用管理员仍不能被停用或降权。

### 10.2 运维责任分层与完整移交

系统按四类身份分离权限，目标是资产所有者平时可以完全不登录 Cloudflare：

| 身份 | 日常职责 | 是否需要 Cloudflare |
|---|---|---|
| 资产所有者 / 兜底负责人 | 保留账户所有权、重大授权和紧急恢复能力 | 平时不需要；仅兜底 |
| 应用管理员 | 新增/停用业务成员、角色、项目/框架范围、规则配置 | 不需要 |
| 技术运维负责人 | 域名、Workers、D1、对象存储、Secrets、WAF、故障与迁移 | 使用自己的 Cloudflare/Notion 运维身份，不共享所有者账号 |
| CI/CD 服务身份 | 自动测试、受控发布和迁移 | 使用专用账户级 API Token，不绑定个人长期身份 |

正式交接前完成一次性基础授权：资产所有者或现有 Super Administrator 邀请受托运维负责人；若要求该负责人今后能独立管理 Cloudflare 成员和账户级 CI Token，则必须明确授予相应高权限，并记录风险。之后开发、发布、迁移、基础设施配置和故障处理均使用受托人的独立身份或 CI 服务身份，不再依赖资产所有者个人登录。业务账号管理完全在应用内完成，与 Cloudflare 成员体系无关。

CI/CD 优先使用 Cloudflare account-owned API token 作为服务身份，按部署实际需要授予最小权限并存入 GitHub Secrets/Environment Secrets；禁止写入仓库、前端、日志或 `.env` 模板。不得使用资产所有者的 Global API Key 或长期个人 Token 作为生产发布依赖。交接验收必须包含：新维护人可在不使用资产所有者登录态的情况下完成一次受控发布、数据库迁移演练和回退；撤销旧维护人的访问后系统与 CI 仍可工作；Token 可轮换且有书面恢复路径。

应用管理员与 Cloudflare 运维角色彼此独立。一个业务管理员不因为能新增系统成员就自动获得 Cloudflare 权限；一个 Cloudflare 技术维护人也不自动获得业务数据管理员权限。

### 10.3 通知与备份

后续若启用邮件通知，联系方式作为可选资料独立维护，不参与登录或身份验证；邮件提供商要求的收件/域名验证属于通知基础设施配置，不等于验证业务账号。实时事件只写通知 outbox，定时器每5分钟处理一小批。规则首次越线及时提醒，持续未解决进入每日摘要；恢复、再次越线或严重程度增加产生新事件。唯一键包含规则版本、对象、发生周期和收件人。失败退避重试、可查询处理状态；不承诺第三方邮件端绝对恰好一次，发送结果未知时保留状态，避免无限重复发送。

当前备份为 D1 绑定分表读取、每 100 行写 `ObjectStorePort` JSON 分片并生成 SHA-256/manifest，每日北京时间 03:00 创建任务，保留 7 份 daily 和 3 份 monthly 已完成备份。它不是跨表一致快照；正式迁移前必须停写、串行备份并完成隔离恢复对账。manifest 仅含附件 key，不含附件本体或内容 hash，正式恢复需另备附件并核对。当前 production provider 为 Notion，应用删除通过归档索引页实现逻辑删除；Notion API 当前不能物理撤销已上传 FileUpload，因此保留策略对 Notion 只能保证应用不可见，不能宣称底层字节已删除。R2/Filesystem 则可实现物理删除。详见 [P7_RUNBOOK.md](P7_RUNBOOK.md)。

## 11. Cloudflare 性能与运行边界

静态前端在浏览器运行；Workers负责鉴权、短请求及轻量业务规则；D1执行索引查询和聚合；`ObjectStorePort` 存附件和备份原件。当前 Cloudflare production 选择 Notion adapter，未来可切 R2；普通服务器使用 Filesystem adapter。大Excel解析和生成文件放浏览器后台线程，服务端仍独立验证。批量任务分片且可恢复，避免全量 JSON 解码/序列化、密集循环和大文件压缩耗尽 Worker CPU。

10ms是每次 Worker 调用的 CPU 执行时间，网络/数据库等待不计入；免费定时器同样受CPU限制。`async`/`waitUntil`不扩大CPU配额。超限会导致操作失败，先前独立提交的数据不会自动回滚，必须靠事务、幂等和任务状态保证恢复。

目标规模：5万行需求样本、5人并发。正式上线在目标地区电信/联通/移动实测，目标常用列表P95≤3秒，已登录首页主要内容≤5秒。这是验收目标，不是已测承诺。Cloudflare免费网络不等于大陆加速；升级Workers Paid不改变这一点。

用量预警继续关注 D1 容量/读写、Workers CPU 和错误率；对象存储按当前 provider 监控。Notion 模式重点观察 API 429/5xx、文件容量和下载失败；R2 模式再观察存储量和操作额度。索引和审计写入也消耗D1额度；不能仅按Excel源行估算。任何付费升级都必须单独授权。
