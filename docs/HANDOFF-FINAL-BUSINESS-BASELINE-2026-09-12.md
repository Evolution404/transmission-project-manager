## 2. 最终业务主线

系统不是简单的“需求 → 物资 → 项目”线性关系。最终主线应为：

```text
需求（抽象业务事项，可带 0..N 条物资子明细）
  ↓
项目储备（关联需求，并形成项目自己的当前物资明细）
  ↓
项目出库（项目级节点：储备项目正式进入执行阶段）
  ↓
执行任务 1..N
  ├─ 任务物资
  │   └─ 物资供应：已上报 / 已发货 / 已到货
  ├─ 实施：完成情况 / 实际物资使用
  └─ 结算：结算范围 / 金额 / 最终标记

任务层的“物资供应 / 实施 / 结算”三条线并行推进。
项目层汇总任务事实。
最终再把实施/结算事实反馈回原始项目需求，形成四状态。
```

## 3. 需求：纯抽象业务事项，但可以带物资

### 3.1 需求本体

需求回答的是：**“有什么业务事项/隐患需要处理？”**

需求本体不依赖物资才能成立。即使暂时没有任何物资明细，一条需求也仍然是合法、完整的业务事项。

建议需求本体至少容纳：

- 序号/需求编号
- 年度
- 电压等级
- 线路名称
- 杆段
- 类别
- 需求描述/技术字段
- 负责人/提出人
- 来源类型与来源追溯
- 版本/创建时间

不同项目类别、全流程要求允许增加扩展字段。

### 3.2 需求物资

需求下面可以有 0..N 条物资子明细，例如：

```text
需求 D001：220kV XX线 #10-#20 防鸟治理
├─ 物资 A 100 套
└─ 物资 B 20 只
```

需求阶段物资表示“提出/导入需求时已经掌握的信息”，可以为空、可以不完整、可以后续变化，**绝不能成为最终项目物资的硬上限**。

Excel 每行即使同时带“物资型号、物资数量”，数据库也不能因此设计成“需求 = 物资行”。导入层应规范化为：

```text
需求本体
+
需求物资子明细
```

只有有可靠业务 ID 或明确归并规则时，才允许把 Excel 多行自动归并成同一需求，不能仅凭线路/杆段相似自行猜测。

### 3.3 需求来源与录入方式

项目需求会来自多个 Excel 需求表。用户同时明确产品级规则：

> 凡支持批量导入的业务对象，必须同时支持手工新建。

因此需求至少提供：

- 新建需求
- 批量导入
- 下载标准模板

手工新增和导入必须走相同服务端业务校验。

来源必须真实区分：

- `manual`：记录创建人/创建时间，不伪造 Excel 文件名、工作表、行号；
- `import`：保留文件 SHA-256、文件名、工作表、物理行号、原始字段。

## 4. 项目储备：关键环节

“根据项目需求形成项目储备、物资明细”是整个系统的关键环节。

项目储备应有两类独立但相关的数据：

1. **关联需求**：这个项目为什么产生；
2. **项目当前物资明细**：这个项目目前预计实际需要什么、多少。

不要再让 `demand_allocations` 同时承担这两种职责。

建议：

```text
project_demand_links
- project_id
- demand_id

project_material_requirements
- project_id
- material/model/unit
- required_quantity
- current version
```

项目物资可以：

- 从需求物资复制作为初始值；
- 手工新增；
- 后续增加、减少、换型；
- 保留修订历史、原因、操作者、时间。

**储备草稿阶段允许 0 条项目物资。** 因为项目储备时未必已经掌握全部物资。不要要求用户一次性把物资全部报齐才能建立项目。

## 5. 项目出库：项目级节点，不是仓库发货

项目储备形成“出库项目”。

这里的“项目出库”含义是：

> 储备项目正式进入执行阶段。

它不是：

- 仓库物资发货；
- “已上报/已发货/已到货”中的任何一个状态；
- 必须逐条项目物资 `release_lines` 扣量的业务动作。

项目出库应更接近项目级事件/快照，至少记录：

- 项目 ID
- 出库时间
- 操作人
- 当时项目/储备版本
- 备注/批准信息

旧 P5 的 `release_lines → implementation_lines → settlement_coverage` 不再是最终业务模型，应纳入结构性重构。

## 6. 项目出库后：一个项目有多个执行任务

项目出库之后才进入任务层。

一个项目可以有很多任务，每个任务有自己的：

- 业务范围
- 任务物资
- 物资供应
- 实施
- 结算

建议第一类对象：

```text
project_tasks
- id
- project_id
- project_release_id
- name / description
- scope / line / section
- owner
- planned_date / completed_date
- version
```

如果需要知道某任务具体落实哪些原始需求，可增加：

```text
task_demand_links
- task_id
- demand_id
```

## 7. 任务物资与物资供应

### 7.1 任务物资

任务有自己的实际执行物资范围：

```text
task_material_requirements
- task_id
- project_material_requirement_id nullable
- material_id nullable
- model / unit
- required_quantity
- version
```

项目储备阶段的项目物资是“项目总体当前物资基线”；任务物资是“这个具体任务实际负责/需要什么”。

一个项目物资可以拆给多个任务。任务物资合计如果要超过项目总体物资，不得静默放大，必须先形成项目物资修订或明确的任务增补变更。

### 7.2 物资供应只发生在项目出库后的任务中

用户明确：**项目出库之后，才会有物资供应。**

供应至少包括：

- 已上报
- 已发货
- 已到货

状态不能挂到全局 `materials` 字典，也不能挂成单个 `status` 覆盖整条物资。

同一任务物资可以同时：

```text
任务 T1 需要 A 60 套
已上报 60
已发货 40
已到货 20
```

因此按数量/批次/事件追踪。

最低不变量：

```text
到货数量 <= 发货数量 <= 上报数量
```

建议使用：

```text
material_supply_batches
或
material_supply_events
```

并至少能追溯：`project → project release → task → task material → supply event/batch`。

## 8. 任务内：物资供应、实施、结算三线并行

这是本轮最重要的纠偏之一。

不要设计成：

```text
供应完成 → 才能实施 → 实施完成 → 才能结算
```

真实关系是：项目出库、任务建立后，三条线并行：

```text
任务 T1
├─ 物资供应
├─ 实施
└─ 结算
```

例如同一时刻完全可以：

```text
任务物资 A：上报60、发货40、到货20
任务实施：完成15
任务结算：已覆盖10
```

它们互不自动推进。

仍保留：

- 实施完成量与实际物资使用量分开；
- 实施与结算独立；
- 允许“未实施已结算”；
- 实施发生后应产生/强化结算提醒；
- 已发生任务/供应/实施/有效结算事实不能被后续修改静默抹掉。

## 9. 四状态最终反馈回项目需求

用户原始要求：按照项目实施实际情况，对**项目需求**形成四种反馈状态：

- 已实施已结算
- 已实施未结算
- 未实施已结算
- 未实施未结算

任务只是执行事实来源。最终系统需要：

```text
任务事实
→ 汇总到项目
→ 再映射/反馈回项目关联的原始需求
```

不能把四状态只停留在任务层或项目层。

部分实施/部分结算应另外显示数量/比例进度；四状态如何从部分事实投影，必须写成明确测试，不允许靠单一 `project.stage` 代替。

## 10. 资金主线

资金线与上述执行任务线并行，不要混成一个状态机。

业务结构：

```text
框架项目 / 整体框架费用
├─ 执行协议 A（预支额度）
├─ 执行协议 B（预支额度）
└─ 多个子项目
    ├─ 子项目预算
    └─ 预算发生
```

明确规则：

- 整体框架费用是总盘子；
- 通过一个或多个执行协议在框架内预支额度；
- 一个执行协议可以用于多个子项目；
- 每个子项目有自己的项目预算；
- **预算发生**的前提是已经有对应执行协议；
- 预算、预算发生、实际费用、结算、协议预支额度是不同事实，不能混加。

月度/季度分析：

```text
每月分析整体项目预算发生情况
Q1 累计目标 25%
Q2 累计目标 50%
Q3 累计目标 75%
Q4 累计目标 100%
```

预警：

- 执行协议预支额度使用达到 90%；
- 整体项目框架费用使用达到 80%；
- 各子项目预算总和超过整体框架费用；
- 进度明显滞后时提醒，并定位明显滞后的子项目。

“明显滞后”的阈值应配置，不要把某个演示版默认值冒充用户已经确认的正式口径。

## 11. 一年工作早知道

用户要求：

> 当遇到“一年工作早知道”文件中的关键事项时间节点时，给出提醒。

因此最终系统应支持把该文件中的关键事项形成可追溯的年度事项/时间节点，并按日期精度提醒。

根据产品级规则，如果支持文件批量导入，也必须保留手工新增/维护入口。

不得为只有月份的数据捏造具体日期。

## 12. 项目储备类别分析

用户要求：

> 根据“项目储备类别”文件中的项目储备大类，分析现状项目储备中各个类别的储备金额占比情况。

该文件用于定义/维护储备大类及映射。

当前最符合 WorkBuddy 参考项目和用户表述的储备金额口径：

```text
某储备大类金额
= 该大类下当前储备项目的物资金额合计

大类占比
= 某大类储备物资金额 / 全部当前储备物资金额
```

不要拿框架预算、预算发生、结算额替代储备金额；施工费/其他费是否纳入储备类别占比没有用户明确授权，不要擅自加入。

## 18. 最终验收示例

系统至少应能完成：

```text
1. 手工建立抽象需求 D001：220kV XX线 #10-#20 防鸟治理；暂时不填物资。
2. 后续给 D001 增加 A 100 套作为当前已知需求物资。
3. 将 D001 纳入储备项目 P001；P001 可以先只有部分物资。
4. 后续复勘把 P001 项目物资调整为 A 80 + B 20，并保留修订历史，不篡改 D001 原始信息。
5. P001 确认项目出库，保存项目级出库快照。
6. 出库后建立 T1、T2 两个执行任务。
7. T1 物资 A 60；供应上报60、发货40、到货20；同时实施15、结算10。
8. T2 物资 A 20 + B 20；可以保持供应/实施/结算均未完成。
9. 项目层汇总 T1/T2，需求 D001 根据实际实施/结算投影到四状态之一，同时保留部分进度。
10. 实施发生后生成结算提醒。
11. 框架/协议/预算发生、月度季度分析、90%/80%/预算超框架预警继续正确。
12. 年度关键事项按文件节点提醒；储备大类按当前储备物资金额计算金额与占比。
```

只有这套链路和自动测试成立，才算本轮重构完成。
