## 用户最新明确业务规则

旧模型“需求物资先完整确定 → 按数量分配到项目”不再成立。

新的主线：

```text
业务需求
→ 项目储备
→ 项目物资需求（可为空、可后补、持续修订）
→ 项目出库（储备项目正式进入执行阶段）
→ 执行任务 1..N
    ├─ 物资供应：已上报 / 已发货 / 已到货
    ├─ 实施：完成量 / 实际物资使用
    └─ 结算：覆盖范围 / 金额 / 最终标记

供应、实施、结算在任务层并行推进。
```

必须遵守：

- 需求是纯抽象业务事项/隐患事项，本体不依赖物资；其下可以附带 0..N 条当时已知的物资明细。物资允许为空、不完整、后续变化，也不能作为最终项目物资硬上限；
- 项目储备允许没有任何物资；
- 最终项目物资可以比最初需求增加、减少、换型，必须保留修订历史；
- 需求和项目用独立多对多关系表达，不要再靠物资数量分配承担立项关系；
- 项目物资需求是储备阶段的总体物资基线；**项目出库是项目级节点/快照，不是仓库物资出库，也不必继续用物资 `release_lines` 表达。** 出库后再建立多个执行任务，任务各自维护物资；任务物资不得无约束放大项目总体需求；
- 标准 `materials` 字典不保存项目状态；
- **只有项目出库之后才允许建立正式执行任务**；任务建立后，“已上报 / 已发货 / 已到货”属于具体任务物资/供应批次；
- 供应状态必须按任务+物资+数量追踪，不能只放一个单值 `status`。例如任务 T1 需要 A 60，可以同时是：上报60、发货40、到货20；
- 至少保证 `到货 <= 发货 <= 上报`；需求减少到已发生供应事实以下必须走显式调整/取消，不得抹历史；
- 项目出库是进入任务执行阶段的前置条件；同一任务内的供应、实施、实际使用、结算是并行的不同事实，不能自动互相生成；项目层只做任务汇总/投影；
- 所有支持批量导入的数据必须同时支持手工新建。

## 建议目标对象


## 测试先行

先写/调整失败测试，再改生产代码。至少覆盖：

- 手工需求创建，来源是真实 `manual`；
- 导入需求仍保留文件/工作表/物理行来源；
- 0 条物资也可以建立储备项目；
- 项目可独立关联需求；
- 项目物资后补、增加、减少、换型并保留历史；
- 未项目出库时创建正式任务/供应/实施/结算必须拒绝；项目出库本身只记录项目进入执行阶段和当时基线，不等同于物资供应；
- 一个出库项目可以创建多个任务，各任务有独立物资、供应、实施、结算；
- 同一任务可并行出现“上报60、发货40、到货20、实施15、结算10”；
- 任务内到货不得超过发货，发货不得超过上报；
- 幂等重试不重复累计供应数量；
- 并发状态推进不超量；
- 已发生出库/任务/供应/实施/有效结算后不能直接删除历史事实；
- 所有批量导入入口都有手工创建入口。
